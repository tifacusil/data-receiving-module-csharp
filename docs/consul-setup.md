## Registered services

Three instances of `data-receiving` are registered, all running on the same host
(`204.168.203.32`) on different ports. This is a single-server simulation of the
three-server topology described in Bai et al. (2020) Table 2.

| Service ID | TCP data port | Health port | Status |
|---|---|---|---|
| `data-receiving-data-receiving-01` | 5000 | 8081 | ✓ passing |
| `data-receiving-data-receiving-02` | 5001 | 8082 | ✓ passing |
| `data-receiving-data-receiving-03` | 5002 | 8083 | ✓ passing |

### Registration details

Each instance is registered automatically by the C# service on startup and
deregistered on graceful shutdown (`ConsulRegistration` hosted service).

**Service name:** `data-receiving`  
**Tags:** `prod`, `version:1.0.0`, `instance:data-receiving-0X`  
**Health check:** HTTP GET to `http://localhost:{HealthPort}/health/` every 10s  
**Auto-deregister:** after 1 minute of critical health checks  

### Important: ServicePort vs TCP data port

The C# service registers with `ServicePort = HealthPort` (8081/8082/8083), not
the TCP data port (5000/5001/5002). This is a known characteristic of the current
implementation. consul-template compensates by computing:

```
TCP data port = ServicePort - 3081
```

## consul-template

consul-template watches the Consul service catalog and regenerates the Nginx
stream upstream block whenever instances are added or removed.

| Item | Path |
|---|---|
| Config file | `/etc/consul-template/consul-template.hcl` |
| Template | `/etc/consul-template/templates/data-receiving.ctmpl` |
| Generated output | `/etc/nginx/stream.d/data-receiving.conf` |
| Reload command | `nginx -s reload` |
| Systemd unit | `consul-template.service` |

### Config (`consul-template.hcl`)

```hcl
consul {
  address = "http://204.168.203.32:8500"
  token   = "<ACL token from secrets file>"
}

template {
  source          = "/etc/consul-template/templates/data-receiving.ctmpl"
  destination     = "/etc/nginx/stream.d/data-receiving.conf"
  command         = "nginx -s reload"
  command_timeout = "10s"
}
```

### Template (`data-receiving.ctmpl`)

```
upstream data_receiving {
{{- range service "data-receiving" }}
    server {{ .Address }}:{{ subtract 3081 .Port }};
{{- end }}
}

server {
    listen 5100;
    proxy_pass data_receiving;
    proxy_timeout 30s;
    proxy_connect_timeout 5s;
}
```

### Generated output (`data-receiving.conf`)

```nginx
upstream data_receiving {
    server 204.168.203.32:5000;
    server 204.168.203.32:5001;
    server 204.168.203.32:5002;
}

server {
    listen 5100;
    proxy_pass data_receiving;
    proxy_timeout 30s;
    proxy_connect_timeout 5s;
}
```

## Nginx stream integration

Nginx acts as a TCP load balancer (Layer 4) in front of the three instances.
DTU sensors (or the Python sender in tests) connect to port 5100; Nginx
distributes connections round-robin across the upstream pool.

| Item | Value |
|---|---|
| Entry point | `204.168.203.32:5100` (TCP) |
| Load balancing | Round-robin (Nginx default) — one instance per connection |
| Stream module | `libnginx-mod-stream` (dynamic, loaded via `modules-enabled`) |
| Nginx config | `stream` block added to `/etc/nginx/nginx.conf` |

## Verifying the setup

```bash
# All 3 instances healthy?
curl -s -H "X-Consul-Token: <token>" \
  "http://204.168.203.32:8500/v1/health/service/data-receiving?passing=true" \
  | python3 -c "import sys,json; [print(s['Service']['ID']) for s in json.load(sys.stdin)]"

# Current Nginx upstream (generated by consul-template)
cat /etc/nginx/stream.d/data-receiving.conf

# Nginx listening on 5100?
sudo ss -tlnp | grep 5100

# consul-template running?
sudo systemctl status consul-template
```

## Fault tolerance behaviour

When an instance is stopped:

1. The C# service calls `Agent.ServiceDeregister` on graceful shutdown — the
   instance is removed from Consul immediately.
2. consul-template detects the change and regenerates `/etc/nginx/stream.d/data-receiving.conf`
   without that instance.
3. Nginx reloads and stops routing new connections to the removed instance.
4. In-flight connections on surviving instances continue unaffected.

Verified on 2026-05-16: stopping instance 02 mid-traffic resulted in 0 frame
loss across 300 frames sent through Nginx port 5100.
